# Эксплуатация

## Первый запуск

`bash scripts/deploy.sh --demo` проверен на чистой Ubuntu 24.04 в локальной VM.
Docker устанавливается из официального apt-репозитория. Сборка требует интернета.
Все данные приложения живут в именованных Docker volumes: PostgreSQL, SeaweedFS,
Caddy и scratch. Секреты находятся в `.env` и `.runtime` вне Git.

На первом запуске init применяет Alembic, создаёт S3 bucket и администратора.
API готов только после БД и хранилища. Worker использует ту же схему и секреты.
При повторном запуске init не меняет пароли существующих пользователей.
Demo seed использует стабильные ID и не создаёт дубликаты. Запускайте его только
на демонстрационной установке: он восстанавливает учебные метаданные.

## HTTPS и смена адреса

Для первой публичной установки: DNS A/AAAA → сервер, TCP 80/443 открыты, затем
`bash scripts/deploy.sh --url https://ваш-домен --demo` (домен в ASCII/punycode).
Caddy сам управляет ACME без выдуманного email. VPS, домен и внешний firewall
в рамках проекта не заказывались. Убедитесь, что сертификат действительно получен
перед передачей личных данных; локальная проверка HTTP этого не доказывает.

Для смены существующего HTTP localhost на домен измените `.env`:
APP_ORIGIN=https://домен, SITE_ADDRESS=домен, COOKIE_SECURE=true,
BIND_ADDRESS=0.0.0.0, HTTP_PORT=80, HTTPS_PORT=443. Затем повторите deploy с этим
`--url`. Скрипт намеренно не перезаписывает существующие секреты. Нельзя оставлять
Secure=false при публичном HTTPS. Внешний HTTP адрес допустим для временного
тестирования, но не для передачи настоящих паролей.

## Наблюдение

```bash
docker compose ps
docker compose logs --tail=100 -f api worker
curl -f http://localhost:8080/api/ready
docker compose exec -T api python -m app.smoke --url http://web --allow-write
```

`/api/health` — жив ли процесс; `/api/ready` — доступны ли БД, миграция и bucket.
В production добавьте внешний мониторинг диска, длины очереди, failed jobs,
срока backup и HTTP 5xx. JSON-логи Docker ограничены ротацией. Локальный API не
публикуется; порты БД и S3 доступны только внутри Docker-сети.

## Резервное копирование

```bash
bash scripts/backup.sh
# Или: bash scripts/backup.sh /absolute/private/backup-directory
bash scripts/restore.sh --replace /absolute/private/backup-directory
```

Backup временно останавливает web/API/worker, делает pg_dump и потоковый tar
объектов S3, сохраняет SHA-256 и версии образов. Пауза нужна для согласованности.
Не выполняйте миграции или другие записи параллельно. Скрипт перезапускает
приложение даже при ошибке backup. Перед копированием убедитесь в сообщении об
успехе и наличии sha256.json. Копия содержит пользовательские данные и хеши
паролей, храните её в закрытом/зашифрованном месте вне этого сервера. Автоматическое
расписание и внешнее хранилище копий ещё не настраивались.

Restore **заменяет БД текущей установки**: требуется явный `--replace`, проверяет
SHA-256, останавливает запись, восстанавливает БД/медиа и отзывает старые сессии.
При ошибке оставляет приложение остановленным. Секреты и `.env` не меняет;
медиа-объекты, отсутствующие в backup, не удаляет (они недоступны без записи БД).
Перед restore сделайте отдельную текущую копию. Регулярно проверяйте восстановление
в отдельной VM. В комплекте тестировался полный цикл на синтетических данных.

## Обновление и остановка

Сначала backup, затем обновление исходников и `bash scripts/deploy.sh` с прежним
`--url`. История миграций версионируется; автоматический rollback релиза не обещается.
`docker compose stop` останавливает сервисы; `docker compose up -d --wait`
запускает снова. `down` сохраняет volumes, `down -v` уничтожает данные.
Scratch — временные файлы, не backup. Нормальная обработка удаляет их; после
аварий старые каталоги можно удалять только при остановленных API/worker.
